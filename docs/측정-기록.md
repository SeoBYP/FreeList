# 측정 기록

무엇을 어떻게 쟀고 몇 번을 다시 쟀는지 남긴 기록입니다. README [작업 내용](../README.md#작업-내용)의 상세판입니다.

## 벽시계 시간은 무엇을 재고 있는지 말해주지 않습니다

**상황**: 순회 비용이 밀집도에 따라 어떻게 변하는지 재려 했습니다. 예상은 "총 시간은 밀집도와 무관하게 일정하고, 원소당 비용만 반비례로 치솟는다"였습니다. 100만 칸을 훑는 건 밀집도와 상관없으니까요.

`Stopwatch`로 잰 숫자는 자료구조의 성능이 아니라 **그 순간 CPU가 실행하던 기계어의 성능**입니다. 아래 세 단계를 거치고서야 둘이 분리됐습니다.

**1차, Debug 빌드로 측정**

```
100% 밀집도:  19.596 ms   (원소당 19.6ns)
기준선 int[]:  1.518 ms   (원소당 1.52ns)
```

Release로 다시 재니 각각 **0.66ms / 0.26ms**였습니다. 열거자 쪽이 30배 빨라졌습니다. Debug에서는 최적화가 꺼져 구조체 열거자의 `MoveNext`와 `Current`가 **인라인되지 않고** 원소마다 실제 메서드 호출이 두 번씩 일어나기 때문입니다.

Debug 숫자로 판단했다면 "튜플 생성과 핸들 구성이 비싸다"는 잘못된 결론에 도달했을 것입니다.

**2차, Release인데 희소 케이스만 6배 느림**

```
칸당 비용 (모두 100만 칸을 훑으므로 비슷해야 정상)
  100%  0.66 ns
   50%  0.57 ns
   10%  0.50 ns
    1%  0.82 ns
  0.1%  3.61 ns    ← 5.9배 이탈
```

메모리 관점에서는 오히려 반대여야 했습니다. 0.1%는 `_items`를 거의 안 읽어 총 4MB만 건드리는데, 100%는 8MB를 읽고도 5배 빨랐습니다.

GC나 측정 순서를 의심해 **밀집도 순서를 뒤집어 다시 측정**했습니다. 이상치가 위치가 아니라 밀집도를 따라갔으므로 순서 아티팩트는 배제됐습니다.

**3차, 회차별 시간을 전부 출력**

중앙값만 보던 것을 7회 측정값 전부로 바꾸자 원인이 드러났습니다.

```
0.1% 회차별:  4.159  3.809  3.649  3.609  3.363  0.343  0.354
                                                  ^^^^^  ^^^^^
                                                  10배 빨라짐
```

**측정 도중에 계층형 컴파일(Tiered Compilation) 승격이 일어났습니다.** .NET은 메서드를 처음엔 최적화가 덜 된 코드(Tier 0)로 컴파일해 시작 속도를 확보하고, 약 30번 호출된 뒤 백그라운드에서 최적화된 코드(Tier 1)로 다시 컴파일해 갈아끼웁니다.

워밍업 30회에 측정 5회, 즉 35번째쯤에 그 교체가 반영된 것입니다. **그전까지 잰 3.6~3.9ms는 전부 Tier 0 숫자였습니다.**

**해결 및 최종 결과**

```
케이스        총 시간(ms)   칸당(ns)   원소당(ns)
기준선 int[]     0.24         0.24        0.24
  0.1%           0.35         0.35      350
  1%             0.45         0.45       45
 10%             0.44         0.44        4.4
 50%             0.56         0.56        1.1
100%             0.85         0.85        0.85
```

칸당 비용이 0.35에서 0.85로 매끄럽게 올라갑니다. 밀집할수록 `Current`가 하는 일이 늘어나니 물리적으로 타당합니다. 2차의 "희소가 6배 느리다"는 통째로 측정 아티팩트였습니다.

**결론: 검토하던 최적화 두 가지 모두 불필요**

| 후보 | 재기 전 판단 | 측정 후 |
|---|---|---|
| 값 전용 열거자 | 원소당 19ns 중 상당수를 줄일 수 있다 | **불필요.** 실제 0.85ns, 기준선 대비 3.5배뿐 |
| dense/sparse 이중 배열 | 희소하면 1000배 낭비 | **불필요.** 전체 순회가 0.35~0.85ms |

두 최적화 모두 이론적으로는 타당해 보였고, 재보지 않았다면 만들었을 것입니다. 구조를 두 배로 복잡하게 만들고 얻는 것은 없었을 것입니다.

**측정에서 겪은 함정 정리**

| 함정 | 증상 | 발견 방법 |
|---|---|---|
| Debug 빌드 | 30배 부풀림 | 실행 경로에 `bin/Debug` 확인 |
| 워밍업 부족 (Tier 0) | 희소 케이스만 10배 느림 | **회차별 값 출력** |
| GC와 측정 순서 | (가설이었고 배제됨) | 밀집도 순서 뒤집기 |
| JIT의 죽은 코드 제거 | 잠재적 위험 | 누적합을 만들어 마지막에 출력 |

**회차별 값을 찍은 것이 결정타였습니다.** `3.898`이라는 요약값 하나는 아무것도 말해주지 않지만, `... 3.363 0.343 0.354`는 모든 것을 말해줍니다. **평균이나 중앙값으로 요약하기 전에 원본 분포를 한 번 봐야 합니다.**

참고로 이 네 가지를 전부 자동으로 처리해주는 도구가 **BenchmarkDotNet**입니다. 안정될 때까지 워밍업을 반복하고, 계층형 컴파일을 기다리고, 분포와 이상치를 보고합니다. 손으로 벤치마크를 짜기 전에 그것부터 고려하는 편이 낫습니다.

**기록: 성능 기준선 (Release, .NET 10, 용량 100만)**

실측값에 식을 맞추면 이렇게 떨어집니다.

```
순회 시간 ≈ 용량 × 0.35ns  +  원소 수 × 0.5ns
              (죽은 칸 스캔)      (Current의 튜플·핸들 생성)
```

| 밀집도 | 예측 | 실측 |
|---|---|---|
| 100% | 0.35 + 0.50 = 0.85ms | 0.85ms |
| 50% | 0.35 + 0.25 = 0.60ms | 0.56ms |
| 10% | 0.35 + 0.05 = 0.40ms | 0.44ms |
| 0.1% | 0.35 + 0.00 = 0.35ms | 0.35ms |

**비용은 `Count`가 아니라 `Capacity`에 비례합니다.** 그리고 `Capacity`는 한 번 커지면 줄어들지 않습니다.

dense/sparse 분리가 없앨 수 있는 것은 앞항, 즉 `용량 × 0.35ns`뿐입니다. 용량 100만에서 그 값은 **0.35ms이고, 60fps 프레임 예산 16.6ms의 2%**입니다. 그걸 아끼자고 `Add`와 `Remove` 전부에 슬롯과 dense의 양방향 매핑, swap-remove 시 마지막 원소 핸들 갱신을 집어넣는 것은 남는 장사가 아닙니다. 순회보다 훨씬 자주 불리는 연산을 무겁게 만드는 거래이기 때문입니다.

**dense 재검토 트리거.** 아래 중 하나라도 해당되면 위 계산이 뒤집히므로 다시 잽니다.

1. **프레임당 순회가 5회 이상.** 시스템 10개가 각자 한 바퀴 돌면 0.35ms가 3.5ms(프레임의 21%)가 됩니다
2. **용량이 1,000만을 넘음.** 선형이라 3.5ms가 되고, 5,000만이면 프레임 예산을 통째로 먹습니다
3. **피크 대비 생존율이 1% 미만으로 장기간 유지됨.** 한때 100만 개가 몰렸다가 지금 1,000개만 살아있어도, 매 순회마다 100만 칸을 여전히 훑습니다. **dense가 존재하는 진짜 이유가 이 상황입니다.** 이번 측정은 처음부터 희소하게 채운 것이라 이 조건을 재현하지 않았습니다

**코드 위치**: `FreeList/Program.cs`

## 속도 136배를 얻으면서 단편화를 두 배로 잃었습니다

빈 블록의 payload에 링크를 심어 명시적 free 리스트를 만들자(3단계) 탐색이 극적으로 줄었습니다.

| 시나리오 | 아레나 걷기 | free 리스트 | 배수 |
|---|---|---|---|
| 작은 것 | 2491.06 | 18.28 | **136배** |
| 섞임 | 426.08 | 4.56 | 93배 |
| 큰 것 | 70.68 | 2.62 | 27배 |

여기까지는 예상대로였습니다. 그런데 단편화율을 같이 보니 반대 방향으로 움직였습니다.

| 시나리오 | 아레나 걷기 | free 리스트 | 빈 블록 수 |
|---|---|---|---|
| 작은 것 | 0.481 | **0.996** | 568 → 1383 |
| 섞임 | 0.192 | **0.954** | 183 → 235 |

원인은 **LIFO**입니다. 아레나를 걷는 방식은 항상 주소가 가장 낮은 적합 블록을 고르므로 할당이 앞쪽에 뭉치고 뒤쪽에 큰 연속 공간이 남습니다. 반면 free 리스트는 최근 해제된 블록을 머리에 꽂으니 주소 순서를 완전히 잃고, 흩어진 조각을 순서 없이 나눠주다 보니 조각이 계속 조각으로 남습니다.

**속도를 136배 얻으면서 공간 효율을 잃은 것입니다.** 재보기 전에는 3단계가 순수한 개선인 줄 알았습니다.

여기서 다음 개선 방향이 나왔습니다. 리스트를 주소 오름차순으로 유지하면 양쪽을 다 가질 수 있습니다. 대가는 `PushFree`가 O(1)에서 O(빈 블록 수)로 오르는 것인데, `Free`가 `TryAlloc`보다 드물다면 남는 장사입니다. 이것도 재보면 됩니다.

> **나중에 재봤고, 이 절의 진단이 틀렸습니다.** 원인은 LIFO가 아니라 first-fit이었습니다. [원인으로 지목한 것을 고쳤는데 효과가 없었습니다](#원인으로-지목한-것을-고쳤는데-효과가-없었습니다)에 기록했습니다.

## 비율 지표의 분자와 분모가 다른 사건을 세고 있었습니다

가변 크기 할당기(변형 B)에서 first-fit과 best-fit 중 무엇을 쓸지 정해야 했습니다. 시간이 환경에 흔들린다는 걸 앞 절에서 확인했으므로 **탐색 횟수**를 세기로 했습니다. 계층형 컴파일도 GC도 Debug 빌드도 카운터는 못 바꾸니까요.

```
탐색/할당 = _probeCount / _allocCount
```

결과가 앞뒤가 안 맞았습니다. 작은 객체 워크로드에서는 first 28.4 대 best 29.7로 **차이가 거의 없는데**, 섞인 크기 워크로드에서는 6.6 대 114.0으로 17배가 났습니다. 같은 두 정책인데 격차가 이렇게 들쭉날쭉할 이유가 없었습니다.

성공한 탐색과 실패한 탐색을 갈라서 다시 재보니 원인이 나왔습니다.

| 시나리오 | 정책 | 전체 탐색 | 성공만 | 실패 몫 |
|---|---|---|---|---|
| 작은 것 8~64B | first | 18.28 | 8.48 | **53.6%** |
| 섞임 8~512B | first | 4.56 | 2.89 | 36.6% |
| 큰 것 256~2048B | first | 2.62 | 2.04 | 22.2% |

**first-fit은 실패할 때 리스트를 끝까지 훑습니다.** 빈 블록이 1285개면 실패 한 번이 1285번의 헛탐색이고, 그 probe는 분자에 들어가는데 분모(성공한 할당 수)에는 안 들어갑니다. 작은 객체 워크로드는 실패율이 1.5%로 높아서 전체 탐색의 절반 이상이 실패 몫이었습니다.

**비율을 정의할 때 분자와 분모가 같은 사건 집합을 세고 있는지 확인하지 않은 것**이 원인입니다. 고치고 나니 격차가 오히려 더 벌어졌습니다.

```
섞임:  first 2.89  vs  best 109.43   →  38배   (17배가 아니라)
```

첫 절의 세 사례는 **측정 환경**(Debug 빌드, JIT 워밍업, 계층형 컴파일)이 숫자를 흔든 경우였습니다. 이번은 다릅니다. 환경은 정확했고 **지표의 정의 자체가 틀렸습니다.** 도구를 바꿔도 안 잡히는 종류입니다.

> **원칙.** 비율을 정의할 때 분자와 분모가 같은 사건 집합을 세고 있는지 확인합니다.

## 탐색 38배 차이가 시간 6배 차이로 나온 이유

섞임 워크로드에서 best-fit은 first-fit보다 탐색을 38배 더 합니다. 그런데 실측 시간은 5.2ms 대 31.4ms로 **6배**밖에 차이가 안 났습니다.

```
추가 탐색 ≈ 106.5회/할당 × 약 10,000 할당 ≈ 1,065,000회
추가 시간 = 31.4 - 5.2 = 26.2ms
         → 탐색 1회 ≈ 25ns ≈ 3GHz에서 80사이클
```

**캐시 미스 한 번 값입니다.** free 리스트 노드는 아레나 여기저기에 흩어져 있고 `ReadNext`는 매번 예측 불가능한 위치를 읽습니다. 순차 접근이 아니라 포인터 추적이라 캐시가 못 도와줍니다.

이건 3단계가 탐색을 136배 줄였는데도 시간이 136배 빨라지지 않는 이유이기도 합니다. 할당 한 번에는 탐색 말고도 헤더와 푸터 쓰기, 리스트 조작, 분할이 들어갑니다. **알고리즘 지표와 실제 시간은 비례하지 않으므로** 둘 다 봐야 합니다.

## 최적 정책은 워크로드가 정합니다

| 시나리오 | 정책 | 탐색/할당 | 실패율 | 단편화율 | 빈블록 | 오버헤드 |
|---|---|---|---|---|---|---|
| 작은 것 8~64B | first | 8.48 | 1.5% | 0.998 | 1285 | 18.5% |
| | **best** | 33.13 | **0.0%** | **0.086** | **92** | 15.4% |
| 섞임 8~512B | **first** | **2.89** | 0.6% | 0.979 | 316 | 2.8% |
| | best | 109.43 | 0.0% | 0.771 | 141 | 2.5% |
| 큰 것 256~2048B | **first** | **2.04** | 0.4% | 0.684 | 70 | 0.6% |
| | best | 42.10 | 0.2% | 0.384 | 68 | 0.7% |

**작은 객체에서는 best-fit이 거의 공짜로 이깁니다.** 단편화가 0.998에서 0.086으로 떨어지고 실패율이 0이 되는데, 탐색은 크게 안 늘어납니다. 단편화가 줄어서 리스트 자체가 짧아지기 때문입니다.

**섞인 크기에서는 first-fit이 압도적으로 쌉니다.** best-fit은 매번 리스트를 끝까지 훑어야 해서 38배를 냅니다.

그리고 오버헤드가 크기에 따라 30배 차이 납니다. 8~64바이트를 다루면 헤더와 푸터 8바이트가 아레나의 **18.5%**를 먹습니다. 256~2048바이트에서는 0.6%입니다. 작은 객체를 가변 크기 할당기에 맡기면 안 되는 이유가 숫자로 나옵니다. 그건 `SlotMap` 같은 고정 크기 풀의 몫입니다.

"어느 정책이 좋은가"에 정답이 없다는 것, 그리고 **워크로드를 정하지 않고는 질문 자체가 성립하지 않는다**는 것이 이 측정의 결론입니다.

## 원인으로 지목한 것을 고쳤는데 효과가 없었습니다

**상황**: 위의 "속도 136배" 절에서 단편화 0.996의 원인을 **LIFO**로 지목했습니다. free 리스트가 최근 해제된 것을 머리에 꽂아 주소 순서를 잃는다는 진단이었습니다.

그래서 리스트를 주소 오름차순으로 유지하는 정책을 만들었습니다(`FreeOrder.Address`). 넣을 때 자리를 찾아 걸어야 하므로 O(1)이 O(빈 블록 수)로 오릅니다. 그 대가를 치를 값어치가 있는지가 질문이었습니다.

**측정 설계**: 축이 셋이 됐습니다.

```
FreeOrder    Lifo / Address        넣는 순서
FitPolicy    First / Best          고르는 방법
워크로드      작은 것 / 섞임 / 큰 것
                                   → 12행
```

그리고 **삽입 탐색을 따로 셌습니다**(`InsertProbeCount`). 이걸 안 세면 `FindFit`에서 줄어든 탐색이 `PushFree`로 옮겨간 것을 "절약"으로 착각하게 됩니다. 앞 절의 분자/분모 교훈을 적용한 것입니다.

```
총탐색/연산 = (전체 탐색 + 삽입 탐색) / (할당 + 해제)
```

**결과** (아레나 256KB, 사용률 70%, 20,000회, Release):

| 워크로드 | 순서 | 정책 | 탐색/할당 | 삽입/해제 | 총/연산 | 단편화율 | 빈블록 |
|---|---|---|---|---|---|---|---|
| 작은 것 8~64B | Lifo | first | 8.48 | 0.00 | 14.10 | 0.998 | 1285 |
| | Lifo | **best** | 29.66 | 0.00 | **14.86** | **0.086** | **92** |
| | Address | first | 153.52 | 159.82 | 156.66 | 0.403 | 491 |
| | Address | best | 37.03 | 24.55 | 30.80 | 0.098 | 97 |
| 섞임 8~512B | Lifo | first | 4.47 | 0.00 | 3.28 | 0.979 | 316 |
| | Lifo | **best** | 114.00 | 0.00 | 56.83 | **0.771** | 141 |
| | Address | first | 117.61 | 118.59 | 118.10 | 0.481 | 250 |
| | Address | best | 122.20 | 68.75 | 95.40 | 0.788 | 160 |
| 큰 것 256~2048B | Lifo | first | 2.24 | 0.00 | 1.29 | 0.684 | 70 |
| | Lifo | **best** | 47.54 | 0.00 | 23.84 | **0.384** | 68 |
| | Address | first | 26.22 | 25.41 | 25.92 | 0.490 | 77 |
| | Address | best | 47.28 | 23.57 | 35.51 | 0.416 | 73 |

### 첫 번째 발견: 주소 순서는 first-fit에만 듣는다

```
first-fit   단편화  0.998 → 0.403,  0.979 → 0.481,  0.684 → 0.490    크게 개선
best-fit    단편화  0.086 → 0.098,  0.771 → 0.788,  0.384 → 0.416    변화 없음
```

best-fit은 **이미 리스트를 끝까지 훑어 가장 딱 맞는 것을 고릅니다.** 순서를 어떻게 바꿔도 고르는 결과가 같습니다. 미세한 악화는 분할 잔여물이 들어가는 자리가 달라진 부수효과입니다.

**주소 순서는 리스트를 끝까지 안 보는 정책에만 의미가 있습니다.**

### 두 번째 발견: 비용이 두 곳에서 동시에 늘었다

```
섞임 first-fit
  삽입/해제    0.00 → 118.59     예상함
  탐색/할당    4.47 → 117.61     예상 못함
```

`FindFit`이 26배 느려진 것은 예상 밖이었습니다. 원인은 **주소 순서가 앞쪽에 작은 조각을 모아둔다**는 것입니다. 큰 요청은 그 조각들을 매번 전부 지나쳐야 뒤쪽 큰 블록에 닿습니다. LIFO는 방금 해제된 큰 블록이 머리에 있어 몇 번에 끝났습니다.

주소 순서가 단편화를 줄이는 메커니즘(작은 조각을 앞에 모아 먼저 소진)과 탐색을 늘리는 메커니즘이 **같은 것**입니다.

### 세 번째 발견: 결론이 뒤집혔다

작은 객체 워크로드에서 두 설정을 나란히 놓으면 이렇습니다.

| | 단편화율 | 총탐색/연산 |
|---|---|---|
| **LIFO + best-fit** | **0.086** | **14.86** |
| 주소 순서 + first-fit | 0.403 | 156.66 |

단편화가 5배 낮고 탐색이 10배 쌉니다. **트레이드오프가 아니라 완전한 우위입니다.**

다만 이것이 세 워크로드 전부에 해당하지는 않습니다. **섞인 크기에서는 단편화 최저가 `주소 순서 + first-fit`(0.481)입니다.**

| 워크로드 | 단편화 최저 설정 | 단편화 | 총탐색/연산 | 차순위 |
|---|---|---|---|---|
| 작은 것 | LIFO + best | **0.086** | 14.86 | 주소순서 + best 0.098 |
| 섞임 | **주소순서 + first** | **0.481** | 118.10 | LIFO + best 0.771 |
| 큰 것 | LIFO + best | **0.384** | 23.84 | 주소순서 + best 0.416 |

섞임에서 주소 순서는 단편화를 0.771에서 0.481로 낮추는 대신 탐색을 56.83에서 118.10으로 두 배 냅니다. **지배가 아니라 맞교환입니다.** 작은 것과 큰 것에서는 맞교환조차 아니고 그냥 손해입니다.

**단편화의 진짜 원인은 리스트 순서가 아니라 고르는 방법이었습니다.** first-fit은 크기를 보지 않고 처음 맞는 것을 줍니다. 400바이트 요청에 2000바이트 블록을 쪼개 주고, 남은 1600이 또 쪼개집니다. 리스트를 아무리 잘 정렬해도 이 낭비는 사라지지 않습니다.

주소 순서는 first-fit의 손해를 절반쯤 줄여주지만, best-fit으로 바꾸면 손해가 애초에 생기지 않습니다.

> **원칙.** 원인으로 지목한 것을 고쳤는데 효과가 없으면, 원인을 잘못 짚은 것입니다.

### 네 번째 발견: 단편화를 싸게 사는 쪽은 정책이다

두 축을 같은 자로 재려면 **"단편화 0.1을 낮추는 데 드는 추가 탐색"**으로 환산합니다. 기준선은 둘 다 기본값인 `LIFO + first-fit`입니다.

| 워크로드 | 정책만 바꿈 (→best) | 순서만 바꿈 (→주소) | 둘 다 바꿈 |
|---|---|---|---|
| 작은 것 | **0.08** | 23.96 | 1.86 |
| 섞임 | 25.75 | **23.06** | 48.23 |
| 큰 것 | **7.52** | 12.70 | 12.77 |

**작은 객체에서 정책 교체는 사실상 공짜입니다.** 0.08은 단편화를 0.998에서 0.086으로 내리면서 탐색을 0.76회 더 냈다는 뜻입니다. 같은 개선을 순서로 사려면 300배를 내야 합니다.

섞임에서만 순서가 근소하게 앞서고(23.06 대 25.75), 큰 것에서는 다시 정책이 유리합니다. 그리고 **셋 다 "둘 다 바꾸기"가 제일 비쌉니다.** 두 축이 서로를 보완하지 않고 비용만 겹칩니다.

### 결론: 무엇을 쓸 것인가

| | 선택 | 근거 |
|---|---|---|
| 기본값 | `LIFO + Best` | 셋 중 둘에서 단편화 최저. 나머지 하나에서도 중간값 |
| 탐색 최우선 | `LIFO + First` | 총탐색 1.29~14.10. 단편화를 포기하는 대가 |
| 주소 순서 | **끈다** | 아래 세 가지 |

주소 순서를 끄는 이유:

1. **best-fit과 조합하면 언제나 순손해.** 같은 블록을 고르면서 삽입 비용만 더 냅니다 (작은 것 14.86 → 30.80)
2. **first-fit과 조합해도 섞임에서만 겨우 본전.** 나머지 둘에서는 정책 교체가 더 쌉니다
3. **이기는 칸에서도 지배가 아니다.** 섞임 단편화 0.771 → 0.481의 대가가 탐색 두 배입니다

구현은 지우지 않고 `FreeOrder` 스위치로 남겼습니다. **"고쳤더니 효과가 없었다"가 이 측정의 결과물**이고, 스위치가 없으면 다음 사람이 같은 가설을 처음부터 다시 검증해야 합니다.

### 정책과 무관한 결론도 하나

| 워크로드 | 오버헤드 |
|---|---|
| 작은 것 8~64B | **18.5%** |
| 섞임 8~512B | 2.8% |
| 큰 것 256~2048B | 0.6% |

헤더와 푸터 8바이트는 블록 크기와 무관하게 고정입니다. 8~64바이트를 다루면 **아레나의 5분의 1이 관리 정보**입니다. 어떤 정책을 골라도 이건 안 줄어듭니다.

**작은 객체는 가변 크기 할당기에 맡기면 안 됩니다.** 그건 `SlotMap` 같은 고정 크기 풀의 몫이고, 거기는 헤더가 아예 없습니다. 변형 A와 변형 B의 경계가 여기서 숫자로 나옵니다.

두 번째 측정에서 "LIFO가 주소 순서를 잃는다"와 "단편화가 올랐다"가 같이 관찰됐고, 그걸 인과로 읽었습니다. 실제로는 **3단계에서 두 가지가 동시에 바뀌었습니다.** 아레나 걷기에서 free 리스트로 바꾸면서 순서도 바뀌었지만, 그전까지 아레나 걷기가 사실상 주소 순서 first-fit이었다는 점이 가려져 있었습니다. 변수를 하나만 바꿨어야 했는데 둘을 바꾼 것입니다.

**가설이 틀렸다는 것을 확인한 것이 이 측정의 성과입니다.** 안 재봤으면 잘못된 인과가 문서에 남았을 것입니다.

## 계층형 컴파일에 두 번째로 걸렸습니다

**상황**: 위 측정의 첫 실행에서 ms 열이 이상했습니다.

```
작은 것 Lifo/First      총탐색 14.10   11.7ms
작은 것 Lifo/Best       총탐색 14.86   15.2ms
작은 것 Address/First   총탐색 156.66  84.0ms
작은 것 Address/Best    총탐색 30.80    2.1ms   ← 탐색 2배인데 7배 빠르다
```

물리적으로 말이 안 됩니다. 탐색 1회당 시간을 계산하니 원인이 드러났습니다.

| 실행 순서 | 설정 | ns/탐색 |
|---|---|---|
| 1 | 작은 것 Lifo/First | **41.5** |
| 2 | 작은 것 Lifo/Best | **51.1** |
| 3 | 작은 것 Address/First | **26.8** |
| 4 | 작은 것 Address/Best | 3.4 |
| 5~12 | 나머지 전부 | 1.9 ~ 5.2 |

**처음 세 행만 10배 이상 느리고, 네 번째부터 안정됩니다.**

**원인**: 계층형 컴파일입니다. 설정마다 바로 앞에서 워밍업 패스를 한 번씩 돌리게 해뒀는데 그것으로 부족했습니다. **Tier 1 승격은 호출 횟수로 예약되고 실제 컴파일은 백그라운드 스레드가 합니다.** 첫 몇 설정이 도는 동안 승격이 진행 중이었고, 네 번째쯤 최적화된 코드로 갈아끼워졌습니다.

첫 번째 측정에서 겪은 것과 **정확히 같은 함정**입니다. 그때는 워밍업 30회로 해결했다고 생각했는데, 설정이 12개로 늘면서 "설정마다 워밍업"이 "전체적으로는 워밍업 부족"이 됐습니다.

**해결**: 워밍업 구조를 바꿨습니다.

```
전       설정 A 워밍업 → 설정 A 측정 → 설정 B 워밍업 → 설정 B 측정 → ...
후       열두 설정 전부 워밍업 x2 → 300ms 대기 → 열두 설정 측정
```

그리고 **같은 함정에 세 번 걸리지 않도록 프로그램이 스스로 진단하게 했습니다.** `ns/탐색` 열을 출력하고, 행 간 편차가 4배를 넘으면 경고를 찍습니다.

```
주의: ns/탐색이 1.9 ~ 41.5로 21.8배 흔들린다.
      측정 환경이 아직 안정되지 않았다는 뜻이므로 ms 열은 비교에 쓰지 마라.
      탐색 횟수 쪽은 카운터라 이 문제의 영향을 받지 않는다.
```

**이번에 즉시 잡힌 이유가 탐색 카운터입니다.** 카운터는 12행 전부 일관됐고 ms만 앞 세 행이 튀었습니다. 두 지표가 어긋나는 것을 보고 **자료구조가 아니라 측정이 흔들렸다**고 판단할 수 있었습니다. 시간만 재고 있었다면 "주소 순서 + best-fit이 압도적으로 빠르다"는 정반대 결론을 냈을 것입니다.

> **원칙.** 환경에 흔들리지 않는 지표(카운터)와 흔들리는 지표(시간)를 같이 재면, 둘이 어긋나는 순간이 곧 측정이 오염된 순간입니다.
