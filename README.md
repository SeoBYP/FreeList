# FreeList

**빈 칸을 어떻게 기억할 것인가.**

미리 배열을 잡아두고 슬롯을 재사용하는 구조에서는 "어느 칸이 비어 있는가"를 어딘가 적어둬야 합니다. Unity DI 라이브러리 VContainer의 `FreeList<T>`를 읽다가 시작해서, 그 답을 두 가지로 직접 만들고, 원본과 비교한 기록입니다.

```
변형 A   SlotMap<T>        고정 크기 칸을 재사용합니다 + 세대 핸들
변형 B   BlockAllocator    가변 크기 바이트 구간을 나눠줍니다 (malloc의 축소판)
```

`.NET 10` · 테스트 117개 · 단일 스레드 · 학습용

---

## 왜 이걸 만들었나

VContainer의 내부를 읽다가 이 코드를 봤습니다.

```csharp
// VContainer 1.19.0 · Runtime/Unity/PlayerLoopRunner.cs
readonly FreeList<IPlayerLoopItem> runners = new FreeList<IPlayerLoopItem>(16);

for (var i = 0; i < span.Length; i++)
{
    var item = span[i];
    if (item != null)                    // ← null을 건너뜁니다
    {
        if (!item.MoveNext())
            runners.RemoveAt(i);         // ← 순회 도중 제거합니다
    }
}
```

두 가지가 걸렸습니다. **`List<T>`면 될 것 같은데 왜 `FreeList<T>`인가**, 그리고 **`null` 검사는 왜 있는가.**

### 답은 하나였습니다

`List<T>.RemoveAt(i)`는 **뒤 원소를 전부 앞으로 당깁니다.**

```
[A][B][C][D]   i=1 에서 B 제거
[A][C][D]      C가 1번으로 당겨짐
      ↑ 다음 반복은 i=2 → D.  C를 건너뜁니다
```

매 프레임 목록을 돌면서 그 안에서 제거하는 코드라 당기면 항목을 놓칩니다. 그래서 **당기지 않고 그 자리를 비웁니다.**

```
[A][B][C][D]  →  [A][   ][C][D]
                       ↑ 인덱스가 안 흔들립니다
```

**당기지 않기 때문에** `List<T>`가 아니고, 당기지 않아서 남은 구멍 때문에 `if (item != null)`이 있습니다. 두 질문의 답이 같았습니다.

그런데 새 질문이 생겼습니다. **저 빈 자리를 나중에 어떻게 다시 찾을까요.**

### 그런데 이건 free list가 아닙니다

VContainer의 답은 이렇습니다.

```csharp
// Runtime/Internal/FreeList.cs
T[] values;

Add(T)  →  values를 처음부터 훑어 null인 자리를 찾습니다     O(n)
```

**매번 찾습니다.** 빈 자리끼리는 아무 관계가 없습니다.

자료구조 이름으로서의 free list는 **두 가지를 동시에 만족**하는 것을 가리킵니다.

> **① 사용 가능한 자원들이 서로를 가리킨다 (연결 리스트)**
> **② 그 링크를 빈 자원 자체의 공간에 저장한다 (추가 메모리 0)**

```
         칸 0     칸 1     칸 2     칸 3     칸 4
_items  [  A  ] [     ] [  C  ] [     ] [  E  ]
_next   [  -  ] [  3  ] [  -  ] [ -1  ] [  -  ]
                   ↑                ↑
_freeHead = 1 ─────┘                └── -1 = 체인 끝

빈 칸 1 → 빈 칸 3 → 끝.   빈 것들이 서로 손을 잡고 있습니다
```

이 둘이 있으면 **"다음 빈 것"을 O(1)에 얻습니다.** 그게 free list라는 이름이 약속하는 것입니다.

| | 빈 자리 재사용 | 빈 것끼리 링크 | 링크를 빈 공간에 | "다음 빈 것" |
|---|---|---|---|---|
| `List<T>` | ✗ | | | |
| VContainer `FreeList<T>` | ✅ | **✗** | | O(n) 탐색 |
| free list | ✅ | ✅ | ✅ | **O(1)** |

VContainer의 것은 정확히 말하면 **구멍 뚫린 배열(sparse array)** 입니다. "빈 자리를 재사용한다"는 목적은 같지만, **자료구조 이름은 목적이 아니라 방법을 가리킵니다.**

②가 왜 필요한지도 짚고 갑니다. 링크는 `Stack<int>`에 빈 인덱스를 쌓아도 만들 수 있습니다. 그런데 원소 100만 개짜리 배열이면 최악의 경우 **100만 개짜리 스택이 하나 더** 생깁니다. 메모리를 아끼려고 만든 구조가 메모리를 두 배로 씁니다. **빈 칸은 어차피 아무도 안 읽으니** 거기에 다음 빈 칸 번호를 적으면 추가 메모리가 0이 됩니다.

**그래서 진짜를 만들어봤습니다.**

## 작업 내용

같은 질문에 두 가지로 답했습니다. **변형 A는 칸 크기가 같다는 전제를 깔고, 변형 B는 그 전제를 뺍니다.**

### 변형 A. `SlotMap<T>`

고정 크기 칸에 free 체인을 만들고, 그 위에 세대를 얹었습니다.

```csharp
var map = new SlotMap<string>(8);

var goblin = map.Add("고블린");      // SlotHandle 반환
map.TryGet(goblin, out var name);    // true, "고블린"

map.Remove(goblin);
map.TryGet(goblin, out _);           // false. 세대가 달라 거부됩니다

foreach (var (handle, value) in map) { /* 살아있는 것만, 할당 없이 */ }
```

#### 재사용된 칸을 어떻게 구분하나

체인을 만들면 바로 다음 문제가 나옵니다. 인덱스만 주고받으면 이런 일이 생깁니다.

```
i = 3 에 A 를 넣음      →  누군가 3을 들고 다닙니다
A 를 제거              →  3번이 비었습니다
B 를 넣음              →  3번이 재사용됩니다

옛 3으로 접근          →  B 가 나옵니다.  거부할 방법이 없습니다
```

인덱스가 곧 신원이라 "몇 번째 주인인가"를 표현할 수 없습니다. 그래서 **발급 회차를 같이 줍니다.**

```csharp
readonly struct SlotHandle
{
    public int Index { get; }
    public int Generation { get; }
}
```

`Remove`가 세대를 올리는 것만으로 **그 칸을 가리키던 모든 옛 핸들이 한 번에 무효**가 됩니다. 옛 핸들 목록을 따로 관리할 필요가 없습니다.

#### 세대 하나가 두 가지를 말합니다

`Add`와 `Remove`가 각각 세대를 1씩 올립니다. 그러면 **상태가 바뀔 때마다 최하위 비트가 토글됩니다.**

```
세대  0  →  Add  →  1  →  Remove  →  2  →  Add  →  3
     짝수         홀수            짝수         홀수
     비었음        살아있음         비었음        살아있음
```

정수 하나가 "몇 번째 주인인가"와 "지금 살아있는가"를 동시에 표현합니다. `bool[] _alives` 배열이 통째로 사라졌습니다.

이 구조에는 이름이 있습니다. Unity DOTS의 `Entity`가 정확히 같은 모양이고, `EntityManager.Exists(entity)`가 위 검사를 합니다.

```csharp
SlotHandle { int Index; int Generation; }     // 이 프로젝트
Entity     { int Index; int Version;    }     // Unity DOTS
```

#### 측정: 순회 비용은 `Count`가 아니라 `Capacity`에 비례합니다

용량 100만, Release. 밀집도를 바꿔가며 전체 순회 시간을 쟀습니다.

| 밀집도 | 살아있는 원소 | 총 시간 |
|---|---|---|
| 0.1% | 1,000 | 0.35ms |
| 10% | 100,000 | 0.44ms |
| 100% | 1,000,000 | 0.85ms |

```
순회 시간 ≈ 용량 × 0.35ns  +  원소 수 × 0.5ns
              (죽은 칸 스캔)     (튜플·핸들 생성)
```

**원소가 1000개든 100만 개든 100만 칸을 훑습니다.** 그리고 `Capacity`는 한 번 커지면 줄지 않습니다.

이 결과로 dense/sparse 분리를 **보류**했습니다. 없앨 수 있는 건 앞항 0.35ms뿐이고, 그건 60fps 프레임 예산의 2%입니다. 구조를 두 배로 복잡하게 만들 값이 아닙니다.

### 변형 B. `BlockAllocator`

변형 A는 free list를 **제일 쉬운 경우로 줄인 것**이었습니다. 칸 크기가 전부 `sizeof(T)`로 같으니 "3번 칸"이라는 말이 성립하고, 그래서 `_next[3]`에 다음 빈 칸 번호를 적을 수 있었습니다.

원형에는 그 전제가 없습니다. free list는 원래 `malloc`의 부품이고, `malloc(64)` 다음 요청이 `malloc(17)`일 수 있습니다. **크기가 같다는 전제를 빼면 free list는 어떻게 될까요.**

```csharp
var alloc = new BlockAllocator(1024);   // 1KB짜리 아레나 하나를 통째로 잡습니다

alloc.TryAlloc(64, out int offset);     // "64바이트 자리 줘"  →  아레나 안의 위치
alloc.AsSpan(offset)[0] = 0xAB;         // 거기에 뭘 쓸지는 호출자 몫입니다

alloc.Free(offset);                     // 반납. 양옆이 비었으면 자동으로 합쳐집니다
```

`SlotMap`은 **값을 받아서 보관해주는 그릇**이고, `BlockAllocator`는 **자리만 나눠주는 관리인**입니다. 후자는 안에 뭐가 들어가는지 모릅니다. `malloc`/`free`가 정확히 이 인터페이스입니다.

#### 관리 정보를 데이터 사이에 심습니다

블록마다 크기가 다르면 몇 번째 블록인지 셀 수가 없고, `_next[]`가 가리킬 대상 자체가 없어집니다.

```
아레나 = byte[] 하나  (64바이트)

 0      4              20   24    28      40   44   48    60   63
[ 24 ][   payload   ][ 24 ][ 20 ][ pay ][ 20 ][ 21 ][ pay ][ 21 ]
 헤더                  푸터  헤더          푸터  헤더          푸터
 └────── 블록 24바이트 ─────┘└─ 블록 20바이트 ─┘└ 블록 20, 비었음 ┘

헤더 = 블록 전체 크기 | (비었으면 1)       21 = 20 | 1
       크기가 4의 배수라 최하위 비트가 늘 비어 있습니다
```

**크기 자체가 다음 블록을 가리키는 링크**가 됩니다. `0 → 24 → 44 → 64(끝)`으로 걸으면 아레나 전체를 훑을 수 있고, 별도 인덱스가 필요 없습니다.

| 자리 | 역할 |
|---|---|
| **헤더** (앞 4B) | 크기 + 빈 플래그. 다음 블록 위치 계산 |
| **푸터** (뒤 4B) | 같은 값의 사본. **앞** 블록 시작을 O(1)로 역산 → 앞쪽 병합 |
| **빈 블록의 payload 앞 8B** | free 리스트의 `prev`/`next` |

**앞에서 말한 ②가 여기서 그대로 다시 나옵니다.** 빈 블록의 payload는 아무도 안 읽으니 링크를 거기 넣습니다. `SlotMap`이 `_next[]` 배열로 하던 걸 별도 배열 없이 재현한 것입니다.

#### 해제하면 양옆을 확인합니다

```
[사용][사용 300][사용]     →  Free(가운데)  →  [사용][빈 300][사용]
                                                    ↑ 합칠 이웃이 없습니다

[빈 300][사용 300][사용]   →  Free(가운데)  →  [    빈 608   ][사용]
                                                    ↑ 앞과 합칩니다. 사라진 헤더와
                                                      푸터 8바이트가 payload로 흡수됩니다
```

앞과 합치려면 **앞 블록이 어디서 시작하는지** 알아야 합니다. 내 헤더 바로 앞 4바이트가 앞 블록의 푸터고, 거기 크기가 적혀 있으니 한 번 빼면 나옵니다. 푸터를 두는 이유가 이것 하나입니다.

합치지 않으면 **빈 공간 900바이트가 300짜리 조각 셋으로 흩어져 500 요청이 실패**합니다. 그게 외부 단편화입니다.

#### 측정: 두 축을 다 재봤습니다

빈 블록을 **고르는 방법**(first-fit / best-fit)과 리스트에 **넣는 순서**(LIFO / 주소 오름차순)를 축으로 두고 세 워크로드에서 12행을 돌렸습니다.

**정책이 단편화를 정합니다.**

| 워크로드 | 정책 | 단편화율 | 할당당 탐색 |
|---|---|---|---|
| 작은 것 8~64B | first | 0.998 | 8.5 |
| | **best** | **0.086** | 29.7 |
| 섞임 8~512B | first | 0.979 | 4.5 |
| | **best** | **0.771** | 114.0 |
| 큰 것 256~2048B | first | 0.684 | 2.2 |
| | **best** | **0.384** | 47.5 |

first-fit은 크기를 안 보고 처음 맞는 것을 줍니다. 400 요청에 2000짜리를 쪼개 주고, 남은 1600이 또 쪼개집니다. **조각을 만듭니다.** best-fit은 크기가 맞는 것끼리 짝지어 주니 **조각을 재활용합니다.**

**순서는 거의 아무것도 안 합니다.**

주소 오름차순으로 유지하는 정책도 만들어 쟀습니다. first-fit에서는 단편화가 좋아졌지만(0.998 → 0.403), **best-fit에서는 변화가 없었습니다**(0.086 → 0.098). best-fit은 이미 리스트를 끝까지 훑어 가장 딱 맞는 것을 고르므로, 순서를 바꿔도 고르는 결과가 같습니다.

그리고 대가로 **총탐색이 11~36배** 늘었습니다. 넣을 때 자리를 찾아 걸어야 하고, 앞쪽에 쌓인 작은 조각을 매번 지나쳐야 하기 때문입니다.

| | 얻은 것 | 낸 것 | 판정 |
|---|---|---|---|
| 정책 first → best | 단편화 −0.21 ~ −0.91 | 탐색 +5% ~ +17배 | **쓴다** |
| 순서 LIFO → 주소 | first-fit에서만 −0.19 ~ −0.60 | 탐색 +11 ~ +36배 | **안 쓴다** |

구현은 `FreeOrder` 스위치로 남겨뒀습니다. "고쳤더니 효과가 없었다"도 결과이고, 스위치가 없으면 다음 사람이 같은 가설을 처음부터 다시 검증해야 합니다.

#### 그런데 최선도 느립니다

네 조합 중 최선은 `LIFO + best-fit`인데, 그 최선의 실제 동작이 이렇습니다.

```
섞임 워크로드   할당 한 번에 빈 블록 114개를 들여다본다
큰 것          47개
```

탐색 1회가 2~5ns이니 **할당 한 번에 300~500ns를 리스트 걷는 데만 씁니다.** 진짜 `malloc`은 할당 한 번이 20~50ns입니다.

원인은 정책도 순서도 아닙니다. **빈 블록 141개를 리스트 하나에 다 꿰어놓고 매번 처음부터 걷는 구조**입니다. best-fit은 정의상 끝까지 훑어야 하니 리스트가 길어지면 답이 없습니다.

**다음 방향은 크기 클래스입니다.** 리스트를 크기 구간별로 쪼개면 요청 크기로 bin을 계산해 그 머리를 뽑으면 되므로 **탐색이 O(1)이 됩니다.** `glibc malloc`, `jemalloc`, `tcmalloc`이 전부 이걸 하고, **단일 free 리스트를 쓰는 실전 할당기는 없습니다.**

다만 단편화가 없어지는 것은 아닙니다. bin을 O(1)로 유지하려면 요청을 bin 크기로 반올림하고 쪼개지 않아야 하는데, 그러면 **낭비가 외부 단편화에서 내부 단편화로 옮겨갑니다.** 65바이트 요청에 128짜리 블록을 통째로 주면 63바이트가 블록 안에서 놉니다.

그리고 지금 지표는 그 비용을 못 봅니다. `단편화율 = 1 - 최대빈블록 / 전체빈공간`은 **빈 공간만** 보는데, 반올림 낭비는 사용 중인 블록 안에 있어 `UsedBytes`로 잡힙니다. 크기 클래스를 넣으면 지표가 "단편화가 극적으로 좋아졌다"고 보고하면서 **실제로 쓸 수 있는 용량이 줄어든 것은 숨깁니다.**

**만들기 전에 자를 먼저 고쳐야 합니다.**

```
내부 단편화율 = 1 - (요청한 바이트 합 / 실제로 준 payload 합)
```

지금 하네스는 요청 크기를 안 들고 있으니 그것부터 추가해야 합니다.

이 측정이 실제로 알아낸 것은 "어느 정책이 좋은가"가 아니라 **"두 축 어느 쪽도 이 구조의 한계를 못 넘는다"**였습니다.

#### 오버헤드는 정책과 무관합니다

| 워크로드 | 오버헤드 |
|---|---|
| 작은 것 8~64B | **18.5%** |
| 섞임 8~512B | 2.8% |
| 큰 것 256~2048B | 0.6% |

헤더와 푸터 8바이트는 블록 크기와 무관하게 고정입니다. 8~64바이트를 다루면 **아레나의 5분의 1이 관리 정보**이고, 어떤 정책을 골라도 안 줄어듭니다.

**작은 객체는 가변 크기 할당기에 맡기면 안 됩니다.** 그건 `SlotMap` 같은 고정 크기 풀의 몫이고, 거기는 헤더가 아예 없습니다. **변형 A와 변형 B의 경계가 이 표입니다.**

→ 측정 전문과 네 번의 실패 기록: [측정 기록](docs/측정-기록.md)

## 결론

다 만들고 나서 VContainer를 다시 읽었습니다. 처음엔 "체인이 없네"로만 보였던 것이, 이번엔 **최적화 방향이 정반대**로 보였습니다.

```
VContainer     순회를 최적화합니다       →  제거가 O(1), 추가는 O(n)이어도 됩니다
이 프로젝트     할당과 해제를 최적화합니다  →  추가와 제거가 O(1), 순회는 밀집도에 맡깁니다
```

### 체인을 안 만든 이유 셋

**① 없는 문제였습니다.** 매 프레임 도는 건 순회지 `Add`가 아닙니다. 기본 용량 16이고 진입점은 보통 수십 개입니다. `Add`가 O(n)이어도 초당 60번 불릴 일이 없습니다.

**② `null`을 고른 순간 체인 둘 자리가 사라집니다.** 링크를 빈 칸에 적으려면 그 자리가 비어 있어야 하는데, `null`이 이미 그 자리를 "비었다는 표시"로 쓰고 있습니다. 둘은 한 세트입니다. 그리고 `null`로 비우는 게 목적 그 자체였습니다. 순회 중 제거 안전성이 목적이고, **재사용은 부산물입니다.**

**③ 상태가 적을수록 잠글 것이 적습니다.** `FreeList`는 `Add`와 `RemoveAt`만 잠그고 순회는 안 잠급니다. 당기지 않으니 순회 인덱스가 안 흔들리고, 상태가 `values` 하나뿐이라 가능한 일입니다.

### 하나의 결정이 세 제약을 낳았습니다

```
"매 프레임 순회하며 그 자리에서 제거"
        ↓
List<T>.RemoveAt은 뒤를 당긴다 → 항목을 건너뛴다
        ↓
당기지 말고 그 자리를 비운다
        ↓
"비었다"를 무엇으로 표시하나 → null (참조 타입이면 공짜)
        ↓
   ┌───────────────┼──────────────────────┐
   ↓               ↓                      ↓
참조 타입만      체인을 적을 자리가 없다      구멍이 배열에 남는다
FreeList<int> 불가  → Add가 O(n)           → 순회가 O(lastIndex+1)
                                          → if (item != null) 검사
```

세 제약이 따로따로가 아니라 **한 결정의 세 얼굴**입니다. 그리고 그 결정은 실수가 아니라 요구에서 강제됐습니다.

### 세 가지 답을 나란히

같은 질문, 그러니까 **빈 것을 어떻게 기억할 것인가**에 셋이 다르게 답했습니다.

| | VContainer `FreeList<T>` | `SlotMap<T>` | `BlockAllocator` |
|---|---|---|---|
| 목적 | 순회하며 스스로를 제거하는 목록 | 안전한 핸들로 접근하는 고정 크기 저장소 | 가변 크기 구간을 나눠주는 관리인 |
| 빈 것 표시 | `null` (데이터 자리에) | 세대 홀짝 (별도 배열에) | 헤더의 빈 플래그 (데이터 사이에) |
| 관리 정보 | **안 만듭니다** (그때그때 찾습니다) | 옆 배열 `_next[]` `_generations[]` | 데이터 사이에 심은 헤더와 푸터 |
| 빈 것 찾기 | 선형 탐색 O(n) | `_freeHead` O(1) | free 리스트 O(빈 블록 수) |
| 식별자 | `int` 인덱스 | `SlotHandle { Index, Generation }` | `int offset` |
| 담을 것 | 참조 타입만 | 값 타입 포함 전부 | 바이트 아무거나 |

**이름이 잘못 붙은 게 아니라, 이름이 가리키는 것보다 덜 만든 것입니다.** 그리고 자기 워크로드에서는 그게 옳습니다. `SlotMap`에서 잰 밀집도 문제도 VContainer에 똑같이 존재하지만 n이 수십 개라 비용이 안 될 뿐입니다.

### 그런데 덜 만든 건 VContainer만이 아닙니다

위 표의 **식별자** 줄을 다시 보면 이상한 게 있습니다. VContainer는 `int` 인덱스라 죽은 핸들을 못 막는다고 지적했는데, `BlockAllocator`도 `int offset`입니다.

`SlotMap`을 만들면서 세대를 붙여 그 문제를 해결해놓고, 정작 다음 구현에서 도로 놓은 것입니다. 의도한 것입니다.

| | `SlotMap<T>` | `BlockAllocator` |
|---|---|---|
| 이중 해제 | 세대로 거부 | 헤더의 빈 플래그로 거부 |
| 재사용된 자리에 옛 식별자 | 거부 | **못 막습니다** |
| 블록 한가운데를 가리키는 위치 | 해당 없음 | **못 막습니다** |

`int offset` 하나로는 "몇 번째 발급분인가"를 표현할 수 없습니다. **C의 `free(ptr)`가 use-after-free를 못 막는 것과 같은 이유**입니다.

막는 방법은 압니다. 헤더에 세대를 두고 핸들을 반환하면 됩니다. 대가는 블록당 4바이트, 오버헤드가 8에서 12로 오릅니다. 그런데 작은 객체 워크로드는 오버헤드가 이미 18.5%였고, 여기에 4바이트를 더하면 27%가 됩니다.

VContainer에 했던 질문을 그대로 제 코드에 하면 답이 같습니다. **덜 만든 것이고, 이 워크로드에서는 그게 옳습니다.** 다른 워크로드에서 틀리는 것도 똑같습니다.

같은 설계, 다른 규모, 다른 결론입니다.

→ 잠금 범위와 세 구현 비교: [VContainer 비교](docs/vcontainer-비교.md)

## 실행

```bash
git clone https://github.com/SeoBYP/FreeList.git
cd FreeList

dotnet build
dotnet test                                  # 117개

dotnet run -c Release --project FreeList     # 할당 정책 측정 (12행)
```

`-c Release`를 빼면 프로그램이 먼저 경고를 찍습니다. Debug 빌드로 재면 숫자가 최대 30배까지 어긋납니다.

측정 프로그램은 `ns/탐색` 열을 같이 찍습니다. 물리적으로는 모든 행이 비슷해야 하는 값이라, **행마다 크게 다르면 재는 환경이 흔들렸다는 뜻**입니다. 4배를 넘으면 프로그램이 경고합니다.

| 대상 | 테스트 | 성격 |
|---|---|---|
| `SlotMap` | 39 | 생성자·Add·Remove·재사용·TryGet·세대·확장·GC·순회·랜덤 |
| `BlockAllocator` | 35 | 생성자·TryAlloc·Free·재사용·분할·병합·무결성·단편화·랜덤 |
| 주소 순서 | 19 | 삽입 위치 4경우·정책 대조·병합·분할·계측·랜덤 |

상당수가 실제로 겪은 버그를 하나씩 붙잡고 있습니다. 랜덤 스트레스는 고정 시드를 써서 실패하면 그대로 재현됩니다.
