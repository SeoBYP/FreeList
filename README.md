# FreeList

**빈 칸을 어떻게 기억할 것인가.**

미리 배열을 잡아두고 슬롯을 재사용하는 구조에서는 "어느 칸이 비어 있는가"를 어딘가 적어둬야 합니다. 그 답을 두 가지로 만들고, 원본이 된 라이브러리와 비교하고, 성능을 측정한 기록입니다.

```
변형 A   SlotMap<T>        고정 크기 칸을 재사용합니다 + 세대 핸들
변형 B   BlockAllocator    가변 크기 바이트 구간을 나눠줍니다 (malloc의 축소판)
                           경계 태그 + 병합 + 명시적 free 리스트
                           고르는 방법(first/best)과 넣는 순서(LIFO/주소)를 바꿔가며 측정
```

`.NET 10` · 테스트 117개 · 단일 스레드 · 학습용

---

## 왜 이걸 만들었나

Unity DI 라이브러리 **VContainer**의 내부를 읽다가 이 코드를 봤습니다.

```csharp
// VContainer 1.19.0 · Runtime/Unity/PlayerLoopRunner.cs
readonly FreeList<IPlayerLoopItem> runners = new FreeList<IPlayerLoopItem>(16);

for (var i = 0; i < span.Length; i++)
{
    var item = span[i];
    if (item != null)                    // ← null을 건너뜁니다
    {
        if (!item.MoveNext())
            runners.RemoveAt(i);         // ← 순회 도중 제거합니다
    }
}
```

두 가지가 걸렸습니다.

1. `List<T>`면 될 것 같은데 왜 `FreeList<T>`인가
2. `null` 검사는 왜 있는가

---

## `null` 검사는 왜 있나

`List<T>.RemoveAt(i)`는 **뒤 원소를 전부 앞으로 당깁니다.**

```
[A][B][C][D]   i=1 에서 B 제거
[A][C][D]      C가 1번으로 당겨짐
      ↑ 다음 반복은 i=2 → D.  C를 건너뜁니다
```

매 프레임 목록을 돌면서 그 안에서 제거하는 코드입니다. 당기면 항목을 놓칩니다.

그래서 **당기지 않고 그 자리를 비웁니다.**

```
[A][B][C][D]  →  [A][   ][C][D]
                       ↑ 인덱스가 안 흔들립니다
```

빈 자리가 배열에 그대로 남으니 순회할 때마다 건너뛰어야 합니다. **그게 `if (item != null)`입니다.**

두 질문의 답이 같았습니다. **당기지 않기 때문에** `List<T>`가 아니고, 당기지 않아서 남은 구멍 때문에 `null` 검사가 있습니다.

그런데 새 질문이 생겼습니다. **저 빈 자리를 나중에 어떻게 다시 찾을까요.**

---

## free list란 무엇인가

VContainer의 답은 이렇습니다.

```csharp
// Runtime/Internal/FreeList.cs
T[] values;

Add(T)  →  values를 처음부터 훑어 null인 자리를 찾습니다     O(n)
```

**매번 찾습니다.** 빈 자리끼리는 아무 관계가 없습니다.

그런데 자료구조 이름으로서의 free list는 그런 게 아닙니다. **두 가지를 동시에 만족**하는 것을 가리킵니다.

> **① 사용 가능한 자원들이 서로를 가리킨다 (연결 리스트)**
> **② 그 링크를 빈 자원 자체의 공간에 저장한다 (추가 메모리 0)**

```
         칸 0     칸 1     칸 2     칸 3     칸 4
_items  [  A  ] [     ] [  C  ] [     ] [  E  ]
_next   [  -  ] [  3  ] [  -  ] [ -1  ] [  -  ]
                   ↑                ↑
_freeHead = 1 ─────┘                └── -1 = 체인 끝

빈 칸 1 → 빈 칸 3 → 끝.   빈 것들이 서로 손을 잡고 있습니다
```

이 둘이 있으면 **"다음 빈 것"을 O(1)에 얻습니다.** 그게 free list라는 이름이 약속하는 것입니다.

| | 빈 자리 재사용 | 빈 것끼리 링크 | 링크를 빈 공간에 | "다음 빈 것" |
|---|---|---|---|---|
| `List<T>` | ✗ | | | |
| VContainer `FreeList<T>` | ✅ | **✗** | | O(n) 탐색 |
| free list | ✅ | ✅ | ✅ | **O(1)** |

VContainer의 것은 정확히 말하면 **구멍 뚫린 배열(sparse array)** 입니다. "빈 자리를 재사용한다"는 목적은 같지만, **자료구조 이름은 목적이 아니라 방법을 가리킵니다.** `List<T>`와 `LinkedList<T>`가 같은 일을 하면서 이름이 다른 것과 같습니다.

### 왜 링크를 빈 공간 안에 넣나

②가 없어도 링크는 만들 수 있습니다. `Stack<int>`에 빈 인덱스를 쌓아두면 됩니다.

```
_items   [ A ][   ][ C ][   ][ E ]
_free    Stack<int> { 1, 3 }        ← 배열이 하나 더 필요합니다
```

동작은 합니다. 그런데 원소 100만 개짜리 배열이면 최악의 경우 **100만 개짜리 스택이 하나 더** 생깁니다. 메모리를 아끼려고 만든 구조가 메모리를 두 배로 씁니다.

**빈 칸은 어차피 아무도 안 읽습니다.** 그 자리에 다음 빈 칸 번호를 적으면 추가 메모리가 0이 됩니다. 이게 free list가 free list인 이유입니다.

## 재사용된 칸은 어떻게 구분하나

체인을 만들고 나면 바로 다음 문제가 나옵니다. 인덱스만 주고받으면 이런 일이 생깁니다.

```
i = 3 에 A 를 넣음      →  누군가 3을 들고 다닙니다
A 를 제거              →  3번이 비었습니다
B 를 넣음              →  3번이 재사용됩니다

옛 3으로 접근          →  B 가 나옵니다.  거부할 방법이 없습니다
```

인덱스가 곧 신원이라 "몇 번째 주인인가"를 표현할 수 없습니다.

그래서 **발급 회차를 같이 줍니다.**

```csharp
readonly struct SlotHandle
{
    public int Index { get; }
    public int Generation { get; }
}
```

`Remove`가 세대를 올리는 것만으로 **그 칸을 가리키던 모든 옛 핸들이 한 번에 무효**가 됩니다. 옛 핸들 목록을 따로 관리할 필요가 없습니다.

### 세대 하나가 두 가지를 말합니다

`Add`와 `Remove`가 각각 세대를 1씩 올립니다. 그러면 **상태가 바뀔 때마다 최하위 비트가 토글됩니다.**

```
세대  0  →  Add  →  1  →  Remove  →  2  →  Add  →  3
     짝수         홀수            짝수         홀수
     비었음        살아있음         비었음        살아있음
```

정수 하나가 "몇 번째 주인인가"와 "지금 살아있는가"를 동시에 표현합니다. `bool[] _alives` 배열이 통째로 사라졌습니다.

```csharp
if ((_generations[index] & 1) == 0) return false;    // 짝수 = 비었음
if (generation != _generations[index]) return false; // 세대 불일치 = 옛 핸들
```

이 구조에는 이름이 있습니다. Unity DOTS의 `Entity`가 정확히 같은 모양이고, `EntityManager.Exists(entity)`가 위 검사를 합니다.

```csharp
SlotHandle { int Index; int Generation; }     // 이 프로젝트
Entity     { int Index; int Version;    }     // Unity DOTS
```

### 다 만들면 이렇게 씁니다

```csharp
var map = new SlotMap<string>(8);

var goblin = map.Add("고블린");      // SlotHandle 반환
map.TryGet(goblin, out var name);    // true, "고블린"

map.Remove(goblin);
map.TryGet(goblin, out _);           // false. 세대가 달라 거부됩니다

foreach (var (handle, value) in map) { /* 살아있는 것만, 할당 없이 */ }
```

여기까지가 **변형 A**입니다. VContainer가 안 만든 체인을 만들고, 그 위에 세대를 얹었습니다.

## 원조 free list는 malloc입니다

변형 A를 만들고 나서 [참고 자료](#참고-자료)의 free list 문서들을 읽는데 죄다 **메모리 할당기** 이야기를 하고 있었습니다. 그럴 만합니다. free list는 원래 `malloc`의 부품이니까요.

지금까지 만든 건 그 개념을 **제일 쉬운 경우로 줄인 것**이었습니다. 칸 크기가 전부 `sizeof(T)`로 같으니 "3번 칸"이라는 말이 성립하고, 그래서 `_next[3]`에 다음 빈 칸 번호를 적을 수 있었습니다.

원형에는 그 전제가 없습니다. `malloc(64)` 다음 요청이 `malloc(17)`일 수 있습니다. **크기가 같다는 전제를 빼면 free list는 어떻게 될까요.** 그게 변형 B를 만든 이유입니다.

### BlockAllocator가 하는 일

`byte[]` 하나를 들고 있다가, **"몇 바이트 줘"에 위치를 돌려줍니다.**

```csharp
var alloc = new BlockAllocator(1024);   // 1KB짜리 아레나 하나를 통째로 잡습니다

alloc.TryAlloc(64, out int offset);     // "64바이트 자리 줘"  →  아레나 안의 위치
alloc.AsSpan(offset)[0] = 0xAB;         // 거기에 뭘 쓸지는 호출자 몫입니다

alloc.Free(offset);                     // 반납. 양옆이 비었으면 자동으로 합쳐집니다
```

`SlotMap`은 **값을 받아서 보관해주는 그릇**이고, `BlockAllocator`는 **자리만 나눠주는 관리인**입니다. 후자는 안에 뭐가 들어가는지 모르고 알 필요도 없습니다. `malloc`/`free`가 정확히 이 인터페이스입니다.

```
new BlockAllocator(1024)  ≈  OS에서 1KB를 한 번 받아옵니다
TryAlloc(64)              ≈  malloc(64)
Free(offset)              ≈  free(ptr)
```

Unity로 치면 `Allocator.Temp`로 잡은 네이티브 메모리를 프레임 안에서 잘라 쓰는 것과 같은 층위입니다. 큰 덩어리를 한 번 잡아두고 그 안에서 나눠 쓰면 진짜 할당이 한 번으로 끝납니다.

### 크기가 다르면 인덱스를 못 매깁니다

**"64바이트 줘"** 를 받는 순간 `_next[]`가 무너집니다. 블록마다 크기가 다르면 몇 번째 블록인지 셀 수가 없고, `_next[]`가 가리킬 대상 자체가 없어집니다.

그래서 **관리 정보를 옆 배열이 아니라 데이터 사이에 심습니다.**

```
아레나 = byte[] 하나  (64바이트)

 0      4              20   24    28      40   44   48    60   63
[ 24 ][   payload   ][ 24 ][ 20 ][ pay ][ 20 ][ 21 ][ pay ][ 21 ]
 헤더                  푸터  헤더          푸터  헤더          푸터
 └────── 블록 24바이트 ─────┘└─ 블록 20바이트 ─┘└ 블록 20, 비었음 ┘

헤더 = 블록 전체 크기 | (비었으면 1)       21 = 20 | 1
       크기가 4의 배수라 최하위 비트가 늘 비어 있습니다
```

**크기 자체가 다음 블록을 가리키는 링크**가 됩니다. `0 → 24 → 44 → 64(끝)`으로 걸으면 아레나 전체를 훑을 수 있고, 별도 인덱스가 필요 없습니다.

| 자리 | 역할 |
|---|---|
| **헤더** (앞 4B) | 크기 + 빈 플래그. 다음 블록 위치 계산 |
| **푸터** (뒤 4B) | 같은 값의 사본. **앞** 블록 시작을 O(1)로 역산 → 앞쪽 병합 |
| **빈 블록의 payload 앞 8B** | free 리스트의 `prev`/`next` |

```
빈 블록:   [헤더4 | prev4 | next4 | ...남은 payload... | 푸터4]
사용 블록: [헤더4 |        사용자 데이터              | 푸터4]
                   ↑ 할당되는 순간 링크는 덮어써집니다
```

**앞에서 말한 ②가 여기서 그대로 다시 나옵니다.** 빈 블록의 payload는 아무도 안 읽으니 링크를 거기 넣습니다. `SlotMap`이 `_next[]` 배열로 하던 걸 별도 배열 없이 재현한 것입니다.

### 해제하면 양옆을 확인합니다

```
[사용][사용 300][사용]     →  Free(가운데)  →  [사용][빈 300][사용]
                                                    ↑ 합칠 이웃이 없습니다. 그대로 둡니다

[빈 300][사용 300][사용]   →  Free(가운데)  →  [    빈 608   ][사용]
                                                    ↑ 앞과 합칩니다. 사라진 헤더와 푸터
                                                      8바이트가 payload로 흡수됩니다
```

앞과 합치려면 **앞 블록이 어디서 시작하는지** 알아야 합니다. 내 헤더 바로 앞 4바이트가 앞 블록의 푸터고, 거기 크기가 적혀 있으니 한 번 빼면 나옵니다. 푸터를 두는 이유가 이것 하나입니다.

합치지 않으면 **빈 공간 900바이트가 300짜리 조각 셋으로 흩어져 500 요청이 실패**합니다. 그게 외부 단편화입니다.

## 재보면 예상이 맞나

**네 번 쟀고, 네 번 다 예상이 틀렸습니다.**

| # | 무엇을 예상했나 | 실제로는 |
|---|---|---|
| 1 | 순회 비용은 살아있는 원소 수에 비례한다 | **용량에 비례한다.** 1000개가 살아도 100만 칸을 훑는다 |
| 2 | free 리스트는 순수한 개선이다 | 탐색을 136배 줄이면서 **단편화를 두 배로 잃었다** |
| 3 | first-fit과 best-fit의 격차는 17배다 | **38배였다.** 지표의 분자와 분모가 다른 사건을 세고 있었다 |
| 4 | 단편화의 원인은 LIFO 순서다 | **first-fit이었다.** 순서를 고쳐도 best-fit에서는 효과가 0이었다 |

### 1. 순회 비용은 `Count`가 아니라 `Capacity`에 비례합니다

용량 100만, `.NET 10` Release. 밀집도를 바꿔가며 전체 순회 시간을 쟀습니다.

| 밀집도 | 살아있는 원소 | 총 시간 |
|---|---|---|
| 0.1% | 1,000 | 0.35ms |
| 10% | 100,000 | 0.44ms |
| 100% | 1,000,000 | 0.85ms |

```
순회 시간 ≈ 용량 × 0.35ns  +  원소 수 × 0.5ns
              (죽은 칸 스캔)     (튜플·핸들 생성)
```

**원소가 1000개든 100만 개든 100만 칸을 훑습니다.** 그리고 `Capacity`는 한 번 커지면 줄지 않습니다.

이 결과로 dense/sparse 분리를 **보류**했습니다. 없앨 수 있는 건 앞항 0.35ms뿐이고, 그건 60fps 프레임 예산의 2%입니다. 구조를 두 배로 복잡하게 만들 값이 아닙니다.

### 2. 탐색을 136배 줄였더니 단편화가 두 배가 됐습니다

`BlockAllocator`에서 아레나를 걷는 대신 빈 블록만 따라가게 바꿨습니다.

| 워크로드 | 탐색: 아레나 걷기 → free 리스트 | 단편화율 |
|---|---|---|
| 작은 것 8~64B | 2491 → 18.3 (**136배**) | 0.481 → **0.996** |
| 섞임 8~512B | 426 → 4.6 (93배) | 0.192 → **0.954** |
| 큰 것 256~2048B | 70.7 → 2.6 (27배) | |

**속도를 얻으면서 공간 효율을 잃었습니다.** 재보기 전에는 순수한 개선인 줄 알았습니다.

이때 원인을 LIFO 순서로 지목했는데, **네 번째 측정에서 그 진단이 틀린 것으로 드러납니다.**

### 3. 최적 정책은 워크로드가 정합니다

성공한 탐색만 세도록 지표를 고친 뒤의 값입니다.

| 워크로드 | 정책 | 탐색/할당 | 단편화율 | 오버헤드 |
|---|---|---|---|---|
| 작은 것 8~64B | first | 8.48 | 0.998 | 18.5% |
| | **best** | 33.13 | **0.086** | 15.4% |
| 섞임 8~512B | **first** | **2.89** | 0.979 | 2.8% |
| | best | 109.43 | 0.771 | 2.5% |

**작은 객체에서는 best-fit이 거의 공짜로 이깁니다.** 단편화가 줄어 리스트 자체가 짧아지므로 탐색이 크게 안 늘어납니다. **섞인 크기에서는 first-fit이 압도적으로 쌉니다.** best-fit은 매번 끝까지 훑어 38배를 냅니다.

표에는 정책과 무관한 숫자도 하나 있습니다. **오버헤드 18.5% 대 2.8%.** 8~64바이트를 다루면 헤더와 푸터 8바이트가 아레나의 5분의 1을 먹습니다. 작은 객체를 가변 크기 할당기에 맡기면 안 되는 이유가 숫자로 나옵니다. 그건 `SlotMap` 같은 고정 크기 풀의 몫입니다.

### 4. 단편화의 원인은 순서가 아니라 first-fit이었습니다

2번에서 지목한 LIFO를 고치려고 주소 오름차순 정책(`FreeOrder.Address`)을 만들고 다시 쟀습니다.

| 워크로드 | 정책 | 단편화율 | 총탐색/연산 |
|---|---|---|---|
| 작은 것 8~64B | first | 0.998 → **0.403** | 14.10 → 156.66 |
| | best | 0.086 → 0.098 | 14.86 → 30.80 |
| 섞임 8~512B | first | 0.979 → **0.481** | 3.28 → 118.10 |
| | best | 0.771 → 0.788 | 56.83 → 95.40 |
| 큰 것 256~2048B | first | 0.684 → **0.490** | 1.29 → 25.92 |
| | best | 0.384 → 0.416 | 23.84 → 35.51 |

<sub>총탐색/연산 = (전체 탐색 + 삽입 탐색) / (할당 + 해제). 주소 순서는 넣을 때도 걸어야 하므로 그 비용을 따로 세어 합쳤습니다.</sub>

**first-fit에서는 좋아졌는데 best-fit에서는 아무 일도 일어나지 않았습니다.**

원인이 순서였다면 정책과 무관하게 효과가 있어야 합니다. **효과가 first-fit에서만 나온다는 건, 고쳐진 것이 순서가 아니라 first-fit의 결함이라는 뜻입니다.**

```
first-fit   크기를 안 보고 처음 맞는 것을 준다
            400 요청에 2000짜리를 쪼개 주고, 남은 1600이 또 쪼개진다
            → 조각을 만든다

best-fit    크기가 맞는 것끼리 짝지어 준다
            → 조각을 재활용한다.  애초에 안 만든다
```

**리스트를 아무리 잘 정렬해도 2000을 쪼개는 행위 자체는 안 없어집니다.** 주소 순서가 first-fit을 절반쯤 구제하는 건, 낮은 주소에 쌓인 조각을 먼저 소진시키기 때문입니다. 자투리 상자를 먼저 뒤지게 만드는 것이지, 자투리가 안 생기게 하는 것이 아닙니다.

그리고 대가가 큽니다. **총탐색이 11~36배**로 늘었습니다. LIFO는 "방금 해제한 크기 = 지금 요청하는 크기"라는 힌트를 공짜로 갖는데, 주소 순서는 그걸 버리기 때문입니다.

| 워크로드 | 단편화 최저 | 값 | 그 값의 탐색 비용 |
|---|---|---|---|
| 작은 것 | LIFO + best | 0.086 | 14.86 |
| 섞임 | 주소순서 + first | **0.481** | 118.10 |
| 큰 것 | LIFO + best | 0.384 | 23.84 |

주소 순서가 이기는 칸이 하나 있지만 지배는 아닙니다. **섞임에서 단편화 0.29를 얻는 대가가 탐색 두 배입니다.**

가설이 틀렸다는 것이 결론이고, **이건 성공한 측정입니다.** 안 재봤으면 잘못된 인과가 문서에 그대로 남았을 겁니다. 구현은 `FreeOrder` 스위치로 남겨뒀습니다.

> 원인으로 지목한 것을 고쳤는데 효과가 없으면, 원인을 잘못 짚은 것입니다.

### 네 번의 공통점

```
1  이론적으로 타당한 최적화 두 개가 재보니 불필요했다
2  개선인 줄 알았던 것이 다른 축에서 손해였다
3  지표의 정의가 틀려 격차가 절반으로 보였다
4  원인이라 믿은 것을 고쳤는데 효과가 없었다
```

**넷 다 "안 재봤으면 그대로 믿었을" 것들입니다.** 그리고 셋은 코드를 아무리 들여다봐도 안 보이는 종류였습니다.

## 다시 원본으로 돌아가서

다 만들고 나서 VContainer를 다시 읽었습니다. 처음엔 "체인이 없네"로만 보였던 것이, 이번엔 **최적화 방향이 정반대**로 보였습니다.

```
VContainer     순회를 최적화합니다       →  제거가 O(1), 추가는 O(n)이어도 됩니다
이 프로젝트     할당과 해제를 최적화합니다  →  추가와 제거가 O(1), 순회는 밀집도에 맡깁니다
```

### 체인을 안 만든 이유 셋

**① 없는 문제였습니다**

```
Add       진입점 등록. 스코프 빌드 시점에 몇 번
RemoveAt  MoveNext()가 false를 반환할 때
순회      매 프레임
```

매 프레임 도는 건 순회지 `Add`가 아닙니다. 기본 용량 16이고 진입점은 보통 수십 개입니다. **`Add`가 O(n)이어도 초당 60번 불릴 일이 없습니다.**

**② `null`을 고른 순간 체인 둘 자리가 사라집니다**

링크를 빈 칸에 적으려면 그 자리가 비어 있어야 하는데, `null`이 이미 그 자리를 "비었다는 표시"로 쓰고 있습니다. **둘은 한 세트입니다.**

그리고 `null`로 비우는 게 목적 그 자체였습니다. 순회 중 제거 안전성이 목적이고, **재사용은 부산물입니다.**

**③ 상태가 적을수록 잠글 것이 적습니다**

`FreeList`는 `Add`와 `RemoveAt`만 잠그고 순회는 안 잠급니다. 당기지 않으니 순회 인덱스가 안 흔들리고, 상태가 `values` 하나뿐이라 가능한 일입니다. `_freeHead`와 `_next[]`를 두면 지켜야 할 불변식이 늘고 무잠금 읽기가 어려워집니다.

### 하나의 결정이 세 제약을 낳았습니다

```
"매 프레임 순회하며 그 자리에서 제거"
        ↓
List<T>.RemoveAt은 뒤를 당긴다 → 항목을 건너뛴다
        ↓
당기지 말고 그 자리를 비운다
        ↓
"비었다"를 무엇으로 표시하나 → null (참조 타입이면 공짜)
        ↓
   ┌───────────────┼──────────────────────┐
   ↓               ↓                      ↓
참조 타입만      체인을 적을 자리가 없다      구멍이 배열에 남는다
FreeList<int> 불가  → Add가 O(n)           → 순회가 O(lastIndex+1)
                                          → if (item != null) 검사
```

세 제약이 따로따로가 아니라 **한 결정의 세 얼굴**입니다. 그리고 그 결정은 실수가 아니라 요구에서 강제됐습니다.

### 세 가지 답을 나란히

같은 질문, 그러니까 **빈 것을 어떻게 기억할 것인가**에 셋이 다르게 답했습니다.

| | VContainer `FreeList<T>` | `SlotMap<T>` | `BlockAllocator` |
|---|---|---|---|
| 목적 | 순회하며 스스로를 제거하는 목록 | 안전한 핸들로 접근하는 고정 크기 저장소 | 가변 크기 구간을 나눠주는 관리인 |
| 빈 것 표시 | `null` (데이터 자리에) | 세대 홀짝 (별도 배열에) | 헤더의 빈 플래그 (데이터 사이에) |
| 관리 정보 | **안 만듭니다** (그때그때 찾습니다) | 옆 배열 `_next[]` `_generations[]` | 데이터 사이에 심은 헤더와 푸터 |
| 빈 것 찾기 | 선형 탐색 O(n) | `_freeHead` O(1) | free 리스트 O(빈 블록 수) |
| 식별자 | `int` 인덱스 | `SlotHandle { Index, Generation }` | `int offset` |
| 담을 것 | 참조 타입만 | 값 타입 포함 전부 | 바이트 아무거나 |

**이름이 잘못 붙은 게 아니라, 이름이 가리키는 것보다 덜 만든 것입니다.** 그리고 자기 워크로드에서는 그게 옳습니다. `SlotMap`에서 잰 밀집도 문제도 VContainer에 똑같이 존재하지만 n이 수십 개라 비용이 안 될 뿐입니다.

### 그런데 덜 만든 건 VContainer만이 아닙니다

위 표의 **식별자** 줄을 다시 보면 이상한 게 있습니다. VContainer는 `int` 인덱스라 죽은 핸들을 못 막는다고 지적했는데, `BlockAllocator`도 `int offset`입니다.

`SlotMap`을 만들면서 세대를 붙여 그 문제를 해결해놓고, 정작 다음 구현에서 도로 놓은 것입니다. 의도한 것입니다.

| | `SlotMap<T>` | `BlockAllocator` |
|---|---|---|
| 이중 해제 | 세대로 거부 | 헤더의 빈 플래그로 거부 |
| 재사용된 자리에 옛 식별자 | 거부 | **못 막습니다** |
| 블록 한가운데를 가리키는 위치 | 해당 없음 | **못 막습니다** |

`int offset` 하나로는 "몇 번째 발급분인가"를 표현할 수 없습니다. **C의 `free(ptr)`가 use-after-free를 못 막는 것과 같은 이유**입니다.

막는 방법은 이미 압니다. 헤더에 세대를 두고 `int` 대신 핸들을 반환하면 됩니다. 대가는 블록당 4바이트, 오버헤드가 8에서 12로 오릅니다. 그런데 [측정에서](#3-최적-정책은-워크로드가-정합니다) 작은 객체 워크로드는 오버헤드가 이미 **18.5%**였습니다. 여기에 4바이트를 더하면 27%가 됩니다.

**안전성과 공간의 맞교환**이고, 교과서적 할당기를 만드는 것이 목적이라 공간을 골랐습니다.

VContainer에 했던 질문을 그대로 제 코드에 하면 답이 같습니다. **덜 만든 것이고, 이 워크로드에서는 그게 옳습니다.** 다른 워크로드에서 틀리는 것도 똑같습니다.

같은 설계, 다른 규모, 다른 결론입니다.

## 실행

```bash
git clone https://github.com/SeoBYP/FreeList.git
cd FreeList

dotnet build
dotnet test                                  # 117개

dotnet run -c Release --project FreeList     # 할당 정책 측정 (12행)
```

`-c Release`를 빼면 프로그램이 먼저 경고를 찍습니다. Debug 빌드로 재면 숫자가 최대 30배까지 어긋납니다.

측정 프로그램은 `ns/탐색` 열을 같이 찍습니다. 물리적으로는 모든 행이 비슷해야 하는 값이라, **행마다 크게 다르면 재는 환경이 흔들렸다는 뜻**입니다. 4배를 넘으면 프로그램이 경고합니다.

| 대상 | 테스트 | 성격 |
|---|---|---|
| `SlotMap` | 39 | 생성자·Add·Remove·재사용·TryGet·세대·확장·GC·순회·랜덤 |
| `BlockAllocator` | 35 | 생성자·TryAlloc·Free·재사용·분할·병합·무결성·단편화·랜덤 |
| 주소 순서 | 19 | 삽입 위치 4경우·정책 대조·병합·분할·계측·랜덤 |

상당수가 실제로 겪은 버그를 하나씩 붙잡고 있습니다. 랜덤 스트레스 2종은 고정 시드를 써서 실패하면 그대로 재현됩니다.
