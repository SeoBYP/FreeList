# FreeList

**빈 칸을 어떻게 기억할 것인가.**

미리 배열을 잡아두고 슬롯을 재사용하는 구조에서는 "어느 칸이 비어 있는가"를 어딘가 적어둬야 한다. 그 답을 두 가지로 만들고, 원본이 된 라이브러리와 비교하고, 성능을 측정한 기록이다.

```
SlotMap<T>        고정 크기 칸 + 세대 핸들
BlockAllocator    가변 크기 블록 + 경계 태그 + 병합 + 명시적 free 리스트
```

`.NET 10` · 테스트 74개 · 단일 스레드 · 학습용

---

## 왜 이걸 만들었나

Unity DI 라이브러리 **VContainer**의 내부를 읽다가 이 코드를 봤다.

```csharp
// VContainer 1.19.0 · Runtime/Unity/PlayerLoopRunner.cs
readonly FreeList<IPlayerLoopItem> runners = new FreeList<IPlayerLoopItem>(16);

for (var i = 0; i < span.Length; i++)
{
    var item = span[i];
    if (item != null)                    // ← null을 건너뛴다
    {
        if (!item.MoveNext())
            runners.RemoveAt(i);         // ← 순회 도중 제거
    }
}
```

두 가지가 걸렸다.

1. `List<T>`면 될 것 같은데 왜 `FreeList<T>`인가
2. `null` 검사는 왜 있는가

---

## `null` 검사는 왜 있나

`List<T>.RemoveAt(i)`는 **뒤 원소를 전부 앞으로 당긴다.**

```
[A][B][C][D]   i=1 에서 B 제거
[A][C][D]      C가 1번으로 당겨짐
      ↑ 다음 반복은 i=2 → D.  C를 건너뛴다
```

매 프레임 목록을 돌면서 그 안에서 제거하는 코드다. 당기면 항목을 놓친다.

그래서 **당기지 않고 그 자리를 비운다.**

```
[A][B][C][D]  →  [A][   ][C][D]
                       ↑ 인덱스가 안 흔들린다
```

빈 자리가 배열에 그대로 남으니 순회할 때마다 건너뛰어야 한다. **그게 `if (item != null)`이다.**

두 질문의 답이 같았다. **당기지 않기 때문에** `List<T>`가 아니고, 당기지 않아서 남은 구멍 때문에 `null` 검사가 있다.

그런데 새 질문이 생겼다 — **저 빈 자리를 나중에 어떻게 다시 찾을까.**

---

## free list란 무엇인가

VContainer의 답은 이렇다.

```csharp
// Runtime/Internal/FreeList.cs
T[] values;

Add(T)  →  values를 처음부터 훑어 null인 자리를 찾는다     O(n)
```

**매번 찾는다.** 빈 자리끼리는 아무 관계가 없다.

그런데 자료구조 이름으로서의 free list는 그런 게 아니다. **두 가지를 동시에 만족**하는 것을 가리킨다.

> **① 사용 가능한 자원들이 서로를 가리킨다 (연결 리스트)**
> **② 그 링크를 빈 자원 자체의 공간에 저장한다 (추가 메모리 0)**

```
         칸 0     칸 1     칸 2     칸 3     칸 4
_items  [  A  ] [     ] [  C  ] [     ] [  E  ]
_next   [  -  ] [  3  ] [  -  ] [ -1  ] [  -  ]
                   ↑                ↑
_freeHead = 1 ─────┘                └── -1 = 체인 끝

빈 칸 1 → 빈 칸 3 → 끝.   빈 것들이 서로 손을 잡고 있다
```

이 둘이 있으면 **"다음 빈 것"을 O(1)에 얻는다.** 그게 free list라는 이름이 약속하는 것이다.

| | 빈 자리 재사용 | 빈 것끼리 링크 | 링크를 빈 공간에 | "다음 빈 것" |
|---|---|---|---|---|
| `List<T>` | ✗ | — | — | — |
| VContainer `FreeList<T>` | ✅ | **✗** | — | O(n) 탐색 |
| free list | ✅ | ✅ | ✅ | **O(1)** |

VContainer의 것은 정확히 말하면 **구멍 뚫린 배열(sparse array)** 이다. "빈 자리를 재사용한다"는 목적은 같지만, **자료구조 이름은 목적이 아니라 방법을 가리킨다.** `List<T>`와 `LinkedList<T>`가 같은 일을 하면서 이름이 다른 것과 같다.

### 왜 링크를 빈 공간 안에 넣나

②가 없어도 링크는 만들 수 있다. `Stack<int>`에 빈 인덱스를 쌓아두면 된다.

```
_items   [ A ][   ][ C ][   ][ E ]
_free    Stack<int> { 1, 3 }        ← 배열이 하나 더 필요하다
```

동작은 한다. 그런데 원소 100만 개짜리 배열이면 최악의 경우 **100만 개짜리 스택이 하나 더** 생긴다. 메모리를 아끼려고 만든 구조가 메모리를 두 배로 쓴다.

**빈 칸은 어차피 아무도 안 읽는다.** 그 자리에 다음 빈 칸 번호를 적으면 추가 메모리가 0이 된다. 이게 free list가 free list인 이유다.

그래서 진짜를 만들어봤다. 만들면서 원본과 갈라지는 지점이 계속 나왔고, 그게 아래 내용이다.

## 재사용된 칸은 어떻게 구분하나

체인을 만들고 나면 바로 다음 문제가 나온다. 인덱스만 주고받으면 이런 일이 생긴다.

```
i = 3 에 A 를 넣음      →  누군가 3을 들고 다닌다
A 를 제거              →  3번이 비었다
B 를 넣음              →  3번이 재사용된다

옛 3으로 접근          →  B 가 나온다.  거부할 방법이 없다
```

인덱스가 곧 신원이라 "몇 번째 주인인가"를 표현할 수 없다.

그래서 **발급 회차를 같이 준다.**

```csharp
readonly struct SlotHandle
{
    public int Index { get; }
    public int Generation { get; }
}
```

`Remove`가 세대를 올리는 것만으로 **그 칸을 가리키던 모든 옛 핸들이 한 번에 무효**가 된다. 옛 핸들 목록을 따로 관리할 필요가 없다.

### 세대 하나가 두 가지를 말한다

`Add`와 `Remove`가 각각 세대를 1씩 올린다. 그러면 **상태가 바뀔 때마다 최하위 비트가 토글된다.**

```
세대  0  →  Add  →  1  →  Remove  →  2  →  Add  →  3
     짝수         홀수            짝수         홀수
     비었음        살아있음         비었음        살아있음
```

정수 하나가 "몇 번째 주인인가"와 "지금 살아있는가"를 동시에 표현한다. `bool[] _alives` 배열이 통째로 사라졌다.

```csharp
if ((_generations[index] & 1) == 0) return false;    // 짝수 = 비었음
if (generation != _generations[index]) return false; // 세대 불일치 = 옛 핸들
```

이 구조에는 이름이 있다. Unity DOTS의 `Entity`가 정확히 같은 모양이고, `EntityManager.Exists(entity)`가 위 검사를 한다.

```csharp
SlotHandle { int Index; int Generation; }     // 이 프로젝트
Entity     { int Index; int Version;    }     // Unity DOTS
```

## 칸 크기가 제각각이면 무엇이 달라지나

여기까지가 `SlotMap<T>`다. 모든 칸이 `sizeof(T)`로 똑같으니 "3번 칸"이라는 말이 성립하고, 그래서 `_next[3]`에 다음 빈 칸 번호를 적을 수 있었다.

**"64바이트 줘"** 를 받는 순간 그게 무너진다. 블록마다 크기가 다르면 몇 번째 블록인지 셀 수가 없고, `_next[]`가 가리킬 대상 자체가 없어진다.

그래서 **관리 정보를 옆 배열이 아니라 데이터 사이에 심는다.**

```
아레나 = byte[] 하나  (64바이트)

 0      4              20   24    28      40   44   48    60   63
[ 24 ][   payload   ][ 24 ][ 20 ][ pay ][ 20 ][ 21 ][ pay ][ 21 ]
 헤더                  푸터  헤더          푸터  헤더          푸터
 └────── 블록 24바이트 ─────┘└─ 블록 20바이트 ─┘└ 블록 20, 비었음 ┘

헤더 = 블록 전체 크기 | (비었으면 1)       21 = 20 | 1
       크기가 4의 배수라 최하위 비트가 늘 비어 있다
```

**크기 자체가 다음 블록을 가리키는 링크**가 된다. `0 → 24 → 44 → 64(끝)`으로 걸으면 아레나 전체를 훑을 수 있고, 별도 인덱스가 필요 없다.

| 자리 | 역할 |
|---|---|
| **헤더** (앞 4B) | 크기 + 빈 플래그. 다음 블록 위치 계산 |
| **푸터** (뒤 4B) | 같은 값의 사본. **앞** 블록 시작을 O(1)로 역산 → 앞쪽 병합 |
| **빈 블록의 payload 앞 8B** | free 리스트의 `prev`/`next` |

```
빈 블록:   [헤더4 | prev4 | next4 | ...남은 payload... | 푸터4]
사용 블록: [헤더4 |        사용자 데이터              | 푸터4]
                   ↑ 할당되는 순간 링크는 덮어써진다
```

**앞에서 말한 ②가 여기서 그대로 다시 나온다.** 빈 블록의 payload는 아무도 안 읽으니 링크를 거기 넣는다. `SlotMap`이 `_next[]` 배열로 하던 걸 별도 배열 없이 재현한 것이다.

### 해제하면 양옆을 확인한다

```
[사용][사용 300][사용]     →  Free(가운데)  →  [사용][빈 300][사용]
                                                    ↑ 합칠 이웃이 없다. 그대로 둔다

[빈 300][사용 300][사용]   →  Free(가운데)  →  [    빈 608   ][사용]
                                                    ↑ 앞과 합친다. 사라진 헤더/푸터
                                                      8바이트가 payload로 흡수된다
```

앞과 합치려면 **앞 블록이 어디서 시작하는지** 알아야 한다. 내 헤더 바로 앞 4바이트가 앞 블록의 푸터고, 거기 크기가 적혀 있으니 한 번 빼면 나온다. 푸터를 두는 이유가 이것 하나다.

합치지 않으면 **빈 공간 900바이트가 300짜리 조각 셋으로 흩어져 500 요청이 실패**한다. 그게 외부 단편화다.

## 30초 만에 써보기

```csharp
// SlotMap — 값을 보관해준다
var map = new SlotMap<string>(8);

var goblin = map.Add("고블린");
map.TryGet(goblin, out var name);    // true, "고블린"

map.Remove(goblin);
map.TryGet(goblin, out _);           // false — 세대가 달라 거부된다

foreach (var (handle, value) in map) { /* 살아있는 것만, 할당 없이 */ }
```

```csharp
// BlockAllocator — 자리만 준다
var alloc = new BlockAllocator(1024);

alloc.TryAlloc(64, out int offset);  // "64바이트짜리 자리 줘"
alloc.AsSpan(offset)[0] = 0xAB;      // 값을 쓰는 건 호출자 몫

alloc.Free(offset);                  // 양옆이 비었으면 자동으로 합쳐진다
```

`SlotMap`은 **값을 보관해주는 그릇**이고 `BlockAllocator`는 **자리를 나눠주는 관리인**이다. 후자는 안에 뭐가 들어가는지 모른다.

## 재보면 예상이 맞나

세 번 쟀고, 세 번 다 예상과 달랐다. 마지막은 구조가 아니라 **자를 잘못 만든** 경우였다.

### 순회 비용은 `Count`가 아니라 `Capacity`에 비례한다

용량 100만, `.NET 10` Release. 밀집도를 바꿔가며 전체 순회 시간을 쟀다.

| 밀집도 | 살아있는 원소 | 총 시간 |
|---|---|---|
| 0.1% | 1,000 | 0.35ms |
| 10% | 100,000 | 0.44ms |
| 100% | 1,000,000 | 0.85ms |

```
순회 시간 ≈ 용량 × 0.35ns  +  원소 수 × 0.5ns
              (죽은 칸 스캔)     (튜플·핸들 생성)
```

**살아있는 게 1000개여도 100만 칸을 훑는다.** 그리고 `Capacity`는 한 번 커지면 줄지 않는다.

이 결과로 dense/sparse 분리를 **보류**했다. 없앨 수 있는 건 앞항 0.35ms뿐이고, 그건 60fps 프레임 예산의 2%다.

### 탐색을 136배 줄였더니 단편화가 두 배가 됐다

`BlockAllocator`에서 아레나를 걷는 대신 빈 블록만 따라가게 바꿨다. 탐색은 극적으로 줄었다.

| 워크로드 | 아레나 전체 걷기 | free 리스트 | 배수 |
|---|---|---|---|
| 작은 것 8~64B | 2491 | 18.3 | **136배** |
| 섞임 8~512B | 426 | 4.6 | 93배 |
| 큰 것 256~2048B | 70.7 | 2.6 | 27배 |

<sub>할당 한 번당 빈 블록을 들여다본 횟수. 이 표는 성공·실패한 탐색을 함께 센다 — 양쪽이 같은 정의라 배수는 유효하다. 아래 정책 비교표는 성공한 탐색만 세는데, 그 이유는 바로 다음 절에 있다.</sub>

그런데 단편화율이 반대로 갔다.

| 워크로드 | 아레나 전체 걷기 | free 리스트 |
|---|---|---|
| 작은 것 | 0.481 | **0.996** |
| 섞임 | 0.192 | **0.954** |

원인은 **LIFO**다. 아레나를 걷는 방식은 늘 주소가 가장 낮은 블록을 고르니 할당이 앞쪽에 뭉치고 뒤에 큰 연속 공간이 남는다. free 리스트는 최근 해제된 걸 머리에 꽂으니 주소 순서를 잃는다.

**속도를 136배 얻으면서 공간 효율을 잃었다.** 재보기 전에는 순수한 개선인 줄 알았다.

### 비율의 분자와 분모가 다른 사건을 세고 있었다

first-fit과 best-fit 중 무엇을 쓸지 정하려고 `탐색 횟수 / 할당 횟수`를 쟀다. 결과가 앞뒤가 안 맞았다 — 작은 객체에서는 28.4 vs 29.7로 차이가 없는데 섞인 크기에서는 17배가 났다. 같은 두 정책의 격차가 이렇게 들쭉날쭉할 이유가 없다.

원인은 **first-fit이 실패할 때 리스트를 끝까지 훑는다**는 것이었다. 빈 블록이 1285개면 실패 한 번이 1285번의 헛탐색이고, 그 탐색은 **분자에 들어가는데 분모(성공한 할당 수)에는 안 들어간다.** 작은 객체는 실패율이 1.5%라 전체 탐색의 **53.6%**가 실패 몫이었다.

성공한 탐색만 다시 세니 격차가 오히려 더 벌어졌다.

| 워크로드 | 정책 | 탐색/할당 | 실패율 | 단편화율 | 오버헤드 |
|---|---|---|---|---|---|
| 작은 것 8~64B | first | 8.48 | 1.5% | 0.998 | 18.5% |
| | **best** | 33.13 | **0.0%** | **0.086** | 15.4% |
| 섞임 8~512B | **first** | **2.89** | 0.6% | 0.979 | 2.8% |
| | best | 109.43 | 0.0% | 0.771 | 2.5% |

**작은 객체에서는 best-fit이 거의 공짜로 이긴다** — 단편화가 줄어 리스트 자체가 짧아지므로 탐색이 크게 안 늘어난다. **섞인 크기에서는 first-fit이 압도적으로 싸다** — best-fit은 매번 끝까지 훑어서 38배(17배가 아니라)를 낸다.

앞의 두 번은 **측정 환경**이 숫자를 흔든 경우였다. 이번은 환경이 정확했고 **지표의 정의가 틀렸다.** 도구를 바꿔도 안 잡히는 종류다.

> 비율을 정의할 때는 분자와 분모가 같은 사건 집합을 세고 있는지 확인한다.

그리고 이 표에는 정책과 무관한 숫자가 하나 더 있다. **오버헤드가 18.5%와 2.8%다.** 8~64바이트를 다루면 헤더+푸터 8바이트가 아레나의 5분의 1을 먹는다. 작은 객체를 가변 크기 할당기에 맡기면 안 되는 이유가 숫자로 나온다 — 그건 `SlotMap` 같은 고정 크기 풀의 몫이다.

"어느 정책이 좋은가"에 정답이 없다. **워크로드를 정하지 않으면 질문 자체가 성립하지 않는다.**

## 다시 원본으로 — VContainer는 왜 그렇게 만들었나

다 만들고 나서 VContainer를 다시 읽었다. 처음엔 "체인이 없네"로만 보였던 것이, 이번엔 **최적화 방향이 정반대**로 보였다.

```
VContainer     순회를 최적화한다       →  제거가 O(1), 추가는 O(n)이어도 된다
이 프로젝트     할당·해제를 최적화한다   →  추가·제거가 O(1), 순회는 밀집도에 맡긴다
```

### 체인을 안 만든 이유 셋

**① 없는 문제였다**

```
Add       진입점 등록 — 스코프 빌드 시점에 몇 번
RemoveAt  MoveNext()가 false를 반환할 때
순회      매 프레임
```

매 프레임 도는 건 순회지 `Add`가 아니다. 기본 용량 16이고 진입점은 보통 수십 개다. **`Add`가 O(n)이어도 초당 60번 불릴 일이 없다.**

**② `null`을 고른 순간 체인 둘 자리가 사라진다**

링크를 빈 칸에 적으려면 그 자리가 비어 있어야 하는데, `null`이 이미 그 자리를 "비었다는 표시"로 쓰고 있다. **둘은 한 세트다.**

그리고 `null`로 비우는 게 목적 그 자체였다 — 순회 중 제거 안전성. **재사용은 부산물이다.**

**③ 상태가 적을수록 잠글 것이 적다**

`FreeList`는 `Add`/`RemoveAt`만 잠그고 순회는 안 잠근다. 당기지 않으니 순회 인덱스가 안 흔들리고, 상태가 `values` 하나뿐이라 가능한 일이다. `_freeHead`와 `_next[]`를 두면 지켜야 할 불변식이 늘고 무잠금 읽기가 어려워진다.

### 하나의 결정이 세 제약을 낳았다

```
"매 프레임 순회하며 그 자리에서 제거"
        ↓
List<T>.RemoveAt은 뒤를 당긴다 → 항목을 건너뛴다
        ↓
당기지 말고 그 자리를 비운다
        ↓
"비었다"를 무엇으로 표시하나 → null (참조 타입이면 공짜)
        ↓
   ┌───────────────┼──────────────────────┐
   ↓               ↓                      ↓
참조 타입만      체인을 적을 자리가 없다      구멍이 배열에 남는다
FreeList<int> 불가  → Add가 O(n)           → 순회가 O(lastIndex+1)
                                          → if (item != null) 검사
```

세 제약이 따로따로가 아니라 **한 결정의 세 얼굴**이다. 그리고 그 결정은 실수가 아니라 요구에서 강제됐다.

### 결론

| | VContainer `FreeList<T>` | 이 프로젝트 `SlotMap<T>` |
|---|---|---|
| 목적 | 매 프레임 순회하며 스스로를 제거하는 목록 | 안전한 핸들로 접근하는 슬롯 저장소 |
| 빈 칸 표시 | `null` — 데이터 자리에 | 세대 홀짝 — 별도 배열에 |
| 빈 칸 찾기 | 선형 탐색 O(n) | `_freeHead` O(1) |
| 죽은 핸들 | 막을 수단 없음 | 세대 불일치로 거부 |
| 담을 타입 | 참조 타입만 | 값 타입 포함 전부 |

**이름이 잘못 붙은 게 아니라, 이름이 가리키는 것보다 덜 만든 것이다.** 그리고 자기 워크로드에서는 그게 옳다. `SlotMap`에서 잰 밀집도 문제도 VContainer에 똑같이 존재하지만 n이 수십 개라 비용이 안 될 뿐이다.

같은 설계, 다른 규모, 다른 결론.

→ 잠금 범위와 세 구현 비교: [VContainer 비교](docs/vcontainer-비교.md)

## 무엇을 막고 무엇을 못 막나

두 구현의 안전성 수준이 **의도적으로 다르다.**

| | `SlotMap<T>` | `BlockAllocator` |
|---|---|---|
| 식별자 | `SlotHandle { Index, Generation }` | `int offset` |
| 이중 해제 | 세대로 거부 | 헤더의 빈 플래그로 거부 |
| 재사용된 자리에 옛 식별자 | 거부 | **못 막는다** |
| 블록 한가운데를 가리키는 위치 | 해당 없음 | **못 막는다** |

`int offset` 하나로는 "몇 번째 발급분인가"를 표현할 수 없다. **C의 `free(ptr)`가 use-after-free를 못 막는 것과 같은 이유**고, 교과서적 할당기를 만드는 것이 목적이라 그대로 뒀다.

막으려면 헤더에 세대를 두고 핸들을 반환하면 된다. 대가는 블록당 4바이트, 오버헤드가 8에서 12로. **안전성과 공간의 맞교환**이고 이 프로젝트는 후자를 골랐다.

## 실행

```bash
git clone https://github.com/SeoBYP/FreeList.git
cd FreeList

dotnet build
dotnet test                                  # 74개

dotnet run -c Release --project FreeList     # 할당 정책 측정
```

`-c Release`를 빼면 프로그램이 먼저 경고를 찍는다. Debug 빌드로 재면 숫자가 최대 30배까지 어긋난다.

| 대상 | 테스트 | 성격 |
|---|---|---|
| `SlotMap` | 39 | 생성자·Add·Remove·재사용·TryGet·세대·확장·GC·순회·랜덤 |
| `BlockAllocator` | 35 | 생성자·TryAlloc·Free·재사용·분할·병합·무결성·단편화·랜덤 |

상당수가 실제로 겪은 버그를 하나씩 붙잡고 있다. 랜덤 스트레스 2종은 고정 시드를 써서 실패하면 그대로 재현된다.
